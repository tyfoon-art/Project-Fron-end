# Design Decisions — Lost & Found ICT

บันทึกเหตุผลของการตัดสินใจออกแบบที่สำคัญ เพื่อให้คนที่มาทำต่อเข้าใจว่า
ทำไมถึงเลือกแบบนั้น และรู้ว่าอะไรควรแก้ได้ / แก้ไม่ได้

แต่ละรายการแบ่งเป็น **สถานะ**
- `ยืนยันแล้ว` — ใช้งานอยู่และเหตุผลยังสมเหตุสมผล
- `ต้องทบทวน` — ทำตามสเปกแล้ว แต่พบจุดที่ควรแก้ ห้ามถือว่าเป็นข้อยกเว้นถาวร

---

## DD-01 ใช้การยืนยันตัวตนแบบกำหนดเองผ่าน RPC แทน Supabase Auth

| | |
|---|---|
| **บริบท** | ต้องมีธรรมาภิบาลที่เข้าใจง่าย และตัดสินใจตอนนั้นว่าจะใช้ฐานข้อมูลอะไร |
| **ตัวเลือกที่พิจารณา** | (ก) `supabase.auth` (ค่าเริ่มต้นของ Supabase), (ข) ตารางผู้ใช้ + RPC ที่เขียนเอง |
| **การตัดสินใจ** | ใช้ตาราง `user_account` + RPC `register_user` / `verify_login` |
| **เหตุผล** | เก็บ `role` และข้อมูลโปรไฟล์ไว้ในตารางเดียวกับบัญชี และควบคุมกระบวนการสมัครสมาชิกได้เอง เหมาะกับงานที่ต้องส่ง schema และ RPC เป็นส่วนหนึ่งของผลงาน |
| **ผลกระทบ** | การบังคับสิทธิ์จริงต้องทำที่ฐานข้อมูล (RLS) เพราะฝั่ง client ปลอมค่า `localStorage` ได้ · ฟีเจอร์ลืมรหัสผ่านของ Supabase Auth ใช้ไม่ได้ → ต้องเขียนใหม่ให้เข้ากับระบบ |
| **สถานะ** | ยืนยันแล้ว (พร้อมข้อจำกัดด้านสิทธิ์ที่ต้องปิดด้วย RLS — ดู GAP_ANALYSIS ปัญหา #4 ในหัวข้อ 7.2) |

## DD-02 บัญชีผู้ใช้ทุกบทบาทอยู่ในตารางเดียว

| | |
|---|---|
| **บริบท** | มีผู้ใช้ 3 กลุ่ม คือ นิสิต/บุคคลทั่วไป, เจ้าหน้าที่, ผู้ดูแลระบบ |
| **ตัวเลือกที่พิจารณา** | (ก) แยก `user_account` กับ `staff_profile` เป็นสองตาราง, (ข) ตารางเดียวแยกด้วย `role` |
| **การตัดสินใจ** | ตารางเดียว `user_account` แยกด้วยคอลัมน์ `role` |
| **เหตุผล** | ลดจำนวนตาราง ลดการ join และตรวจสอบว่า “คนนี้เป็นใคร” ได้จากที่เดียว เจ้าหน้าที่ก็ยังเป็นผู้ใช้ที่ยื่นคำร้องได้ |
| **ผลกระทบ** | โปรไฟล์เจ้าหน้าที่จัดการผ่าน `staff_upsert_profile` / `staff_update_avatar` บนตารางเดียวกัน · ตาราง `staff_profile` ในเอกสารเดิมถูกลบออกแล้ว |
| **สถานะ** | ยืนยันแล้ว |

## DD-03 ใช้ `item` เป็นตารางหลัก แยกความหายกับการพบไว้ใน `report`

| | |
|---|---|
| **บริบท** | หน้าจอเดียวต้องแสดงทั้งของที่พบและของที่หาย |
| **ตัวเลือกที่พิจารณา** | (ก) ตารางเดียวเก็บทุกอย่าง, (ข) `item` เป็นตัวกลาง แล้วแยกใบแจ้งตามชนิดเป็น `report` |
| **การตัดสินใจ** | `item` เก็บสิ่งที่มีอยู่จริงหนึ่งชิ้น + สถานะ + ตำแหน่ง ส่วน `report` เก็บ “เหตุการณ์” (หาย/พบ, เวลา, สถานที่) อ้าง `item_id` |
| **เหตุผล** | หนึ่งชิ้นของสามารถมีหลายเหตุการณ์และหลายคำร้องได้ โดยไม่ต้องคัดลอกข้อมูลสิ่งของ ทำให้ประวัติและการอ้างอิงไม่แตกแยก · ตรงกับหลักการฐานข้อมูลเป็นแหล่งความจริงเดียว (KP-01) |
| **ผลกระทบ** | หน้ารายละเอียดต้อง join `report` เพื่อรู้ว่าเป็นของหายหรือของพบ (`src/js/detail.js`) — จุดที่มักเกิดบั๊กเพราะสองอย่างนี้ถูกใช้คนละที่ในโค้ด |
| **สถานะ** | ยืนยันแล้ว |

## DD-04 เก็บตำหนิลับแยกไว้ในตาราง `item_secret` และอ่านผ่าน RPC เท่านั้น

| | |
|---|---|
| **บริบท** | ต้องให้เจ้าหน้าที่เทียบตำหนิกับของจริง แต่ห้ามทั่วไปเห็น และต้องกันการอ่านข้ามระบบ |
| **ตัวเลือกที่พิจารณา** | (ก) เก็บในคอลัมน์ของ `item` แล้วซ่อนด้วย JavaScript, (ข) เก็บในตารางแยกและปิดสิทธิ์ด้วย RLS |
| **การตัดสินใจ** | ตาราง `item_secret` + RPC `get_staff_defect_note` |
| **เหตุผล** | ซ่อนด้วย JavaScript อย่างเดียวไม่พอ เพราะผู้ใช้เรียกอ่านตารางตรง ๆ จากเบราว์เซอร์ได้ การแยกตารางทำให้ “ไม่มีสิทธิ์อ่าน” บังคับได้จริงระดับฐานข้อมูล |
| **ผลกระทบ** | ฝั่งหน้าเว็บอ่าน `item` ได้ตามปกติ แต่ต้องเรียก RPC เพื่อดูตำหนิลับ · ข้อมูลลับจึงไม่ควรอยู่ใน `item` หรือ `report` |
| **สถานะ** | ยืนยันแล้ว (แต่ต้องยืนยันว่า `create_report` บันทึกรูปลับลง `item_secret` จริง ไม่ใช่ลง `report` — ดู GAP_ANALYSIS ปัญหา #2 ในหัวข้อ 7.2) |

## DD-05 ใช้ RLS + RPC เป็นชั้นควบคุมสิทธิ์ และหน้าจอทำหน้าซ่อนข้อมูลซ้ำอีกชั้น

| | |
|---|---|
| **บริบท** | ต้องกันทั้งการเรียกข้อมูลผิดสิทธิ์ และการแสดงค่าที่ไม่ควรเห็น |
| **ตัวเลือกที่พิจารณา** | (ก) ตรวจสิทธิ์ที่หน้าจออย่างเดียว, (ข) RLS ที่ฐานข้อมูลอย่างเดียว, (ค) ทั้งสองชั้น |
| **การตัดสินใจ** | สองชั้น: RLS บังคับที่ฐานข้อมูล และหน้าจอซ่อน/จัดรูปแบบค่าอีกชั้น (BR-03, KP-03) |
| **เหตุผล** | ชั้นที่ฐานข้อมูลรับประกันความปลอดภัย ชั้นที่หน้าจอทำให้ผู้ใช้เข้าใจสถานะสิทธิ์ของตนและลดโอกาสเรียกข้อมูลผิดโดยไม่ตั้งใจ |
| **ผลกระทบ** | ต้องเขียนนโยบาย RLS ให้ครบทุกตาราง และเขียนเอกสาร `rls.sql` เป็นส่วนหนึ่งของการส่งมอบ (D-07) |
| **สถานะ** | ยืนยันแล้ว |

## DD-06 ยึด “สถานะ” เป็นตัวกำหนดพฤติกรรมของทุกหน้า

| | |
|---|---|
| **บริบท** | ระบบมีหลายบทบาทและหลายขั้นตอน ต้องไม่ให้ผู้ใช้ทำข้ามขั้น |
| **ตัวเลือกที่พิจารณา** | (ก) ตรวจสิทธิ์จากสถานะในตาราง, (ข) เก็บสถานะไว้หลายที่ |
| **การตัดสินใจ** | `item.status` เป็นตัวตัดสินใจหลักว่าจะเห็นปุ่มอะไร และเปลี่ยนสถานะได้เฉพาะลำดับที่กำหนด (KP-02, BR-05) |
| **เหตุผล** | ทำให้หน้าจอหลายหน้าทำนายพฤติกรรมได้เหมือนกัน โดยไม่ต้องเขียนตรรกะซ้ำ |
| **ผลกระทบ** | ต้องกำหนดค่าสถานะให้ครบและใช้ชื่อเดียวกันทุกไฟล์ — ปัจจุบันโค้ดใช้ `รอตรวจสอบ` แต่เอกสารเดิมระบุ `แจ้งพบ` ต้องเลือกชุดค่าเดียวแล้วแก้ให้ตรงกัน |
| **สถานะ** | ต้องทบทวน (ชุดค่าสถานะในเอกสารยังไม่ตรงกับโค้ดจริง) |

## DD-07 ย้ายตรรกะที่กระทบหลายตารางไปไว้ที่ฐานข้อมูล (RPC)

| | |
|---|---|
| **บริบท** | การรับฝาก/ส่งมอบ/จำหน่าย ต้องแตะหลายตารางและมีเงื่อนไขหลายข้อ |
| **ตัวเลือกที่พิจารณา** | (ก) เขียนอัปเดตจากหน้าเว็บหลายคำขอ, (ข) เรียก RPC เดียวจบ |
| **การตัดสินใจ** | ให้หน้าเว็บเรียก `staff_receive_item`, `record_handover`, `staff_dispose_item` เท่านั้น (KP-06) |
| **เหตุผล** | ตรรกะเดียว ไม่มีสถานะกลางอาการ และตรวจสอบย้อนหลังได้จากนิยามฟังก์ชัน |
| **ผลกระทบ** | ถ้า RPC ยังไม่ครบ ระบบจะทำงานไม่ได้แม้หน้าเว็บถูกต้อง — ต้องถือว่า RPC คือส่วนหนึ่งของโค้ดที่ต้องทดสอบ (D-06) |
| **สถานะ** | ยืนยันแล้ว |

## DD-08 ยกเลิกโพสต์แบบ Soft Delete ด้วย `deleted_at`

| | |
|---|---|
| **บริบท** | โพสต์ถูกอ้างอิงจากคำร้อง ห้อง และประวัติ ห้ามหายไปเฉย ๆ |
| **ตัวเลือกที่พิจารณา** | (ก) `DELETE` จริง, (ข) ตั้ง `deleted_at` แล้วกรองออกจากรายการ |
| **การตัดสินใจ** | Soft Delete (KP-05) |
| **เหตุผล** | รักษาความถูกต้องของข้อมูลอ้างอิงและตรวจสอบย้อนหลังได้ โดยไม่เสียประวัติ |
| **ผลกระทบ** | ทุกจุดที่อ่าน `item` ต้องเติมเงื่อนไข `.is('deleted_at', null)` — ปัจจุบันทำแล้วเกือบทุกหน้า ต้องระวังไม่ให้ตกหล่นในจุดใหม่ |
| **สถานะ** | ยืนยันแล้ว |

## DD-09 จุดเก็บของเป็นข้อมูลหลัก (Master Data) ที่แยกเก็บ

| | |
|---|---|
| **บริบท** | ต้องเพิ่ม/ปิดจุดเก็บของได้โดยไม่แก้โค้ด และต้องผูกกับตำแหน่งจัดเก็บจริง (BR-02) |
| **ตัวเลือกที่พิจารณา** | (ก) เขียนเป็นค่าคงที่ในโค้ด, (ข) เก็บเป็นตาราง `storage_point` |
| **การตัดสินใจ** | ตาราง `storage_point` อ้างจาก `item.current_storage_id` และมี `is_active` เพื่อปิดจุดที่เลิกใช้ |
| **เหตุผล** | ผู้ดูแลระบบต้องจัดการได้เอง และรายการที่อยู่ในจุดเก่าต้องยังอ้างอิงจุดเดิมได้ |
| **ผลกระทบ** | การลบจุดเก็บของต้องเป็นการปิดใช้งาน ไม่ใช่ลบแถวจริง — มี RPC `admin_delete_storage_point` รองรับ |
| **สถานะ** | ยืนยันแล้ว |

## DD-10 คำนวณอายุการจัดเก็บ 90 วันฝั่งหน้าเว็บ

| | |
|---|---|
| **บริบท** | ต้องรู้ว่าของชิ้นใดเกินกำหนด เพื่อเตือนและให้จำหน่ายได้ (BR-08, F-09) |
| **ตัวเลือกที่พิจารณา** | (ก) คำนวณในหน้าเว็บทุกครั้งที่เปิดหน้า, (ข) คำนวณในฐานข้อมูลแล้วเก็บเป็นฟิลด์ |
| **การตัดสินใจ** | คำนวณในหน้าเว็บจาก `item.created_at` เทียบกับวันปัจจุบัน |
| **เหตุผล** | เรียบง่าย ไม่ต้องมีงานค้างให้รันทุกวัน และข้อมูลที่ใช้มีน้อย |
| **ผลกระทบ** | ต้องนับจาก “วันที่รับฝาก” ไม่ใช่ `created_at` มิฉะนั้นของที่ค้างจริงจะถูกจัดเป็นเกินกำหนดเร็วเกินจริง — **ต้องแก้** |
| **สถานะ** | ต้องทบทวน |

## DD-11 กรองผลการค้นหาในฝั่งหน้าเว็บ

| | |
|---|---|
| **บริบท** | หมวดหมู่/วันที่/สถานที่/สถานะ ต้องทำงานพร้อมกัน (F-04) |
| **ตัวเลือกที่พิจารณา** | (ก) โหลดข้อมูลทั้งหมดแล้วกรองในเบราว์เซอร์, (ข) ส่งเงื่อนไขไปให้ฐานข้อมูลกรอง |
| **การตัดสินใจ** | ดึงรายการที่ยังไม่ปิดเคสมาทั้งหมด แล้วกรองฝั่ง client |
| **เหตุผล** | ไม่ต้องเขียน query ซับซ้อน เหมาะกับปริมาณข้อมูลระดับคณะ และทำให้การทำงานแบบออฟไลน์เป็นจริงในระดับหน้า |
| **ผลกระทบ** | เมื่อข้อมูลมากขึ้นจะช้าลงและดึงข้อมูลเกินจำเป็น — ต้องเพิ่ม pagination และ debounce เมื่อถึงเวลา |
| **สถานะ** | ต้องทบทวน |

## DD-12 เก็บรูปภาพสินค้าเป็น base64 ในฐานข้อมูล (ข้อจำกัดของสถานะปัจจุบัน)

| | |
|---|---|
| **บริบท** | ฟอร์มแจ้งพบ/แจ้งหายส่งรูปไปกับ RPC ทั้งรูปหลักและรูปลับ |
| **ตัวเลือกที่พิจารณา** | (ก) อัปโหลดขึ้น Object Storage แล้วเก็บ URL, (ข) แปลงเป็น base64 เก็บในคอลัมน์ |
| **การตัดสินใจ (ปัจจุบัน)** | base64 ในคอลัมน์ (`report3.js`, `staff-inventory-add.js`) ขณะที่หลักฐานคำร้อง/การส่งมอบ/รูปโปรไฟล์ใช้ Object Storage |
| **เหตุผลของโค้ดปัจจุบัน** | ทำให้ส่งพร้อมคำขอเดียวได้ ไม่ต้องจัดการสิทธิ์ของไฟล์ในขั้นตอนสร้างโพสต์ |
| **เหตุผลที่ควรเปลี่ยน** | ขัดกับ KP-07/TS-04 ที่กำหนดให้เก็บไฟล์ไว้บน Storage ตารางบวมเร็ว คิวรีช้าลง และเสี่ยงทำให้รูปลับหลุดออกจาก `item_secret` |
| **สถานะ** | ต้องทบทวน (ควรย้ายไป Storage ก่อนส่งมอบ) |

## DD-13 ไม่สร้าง REST API แยก ใช้การเรียก Supabase โดยตรง

| | |
|---|---|
| **บริบท** | โครงสร้างเว็บแบบหลายหน้า ไม่มี server แยก |
| **ตัวเลือกที่พิจารณา** | (ก) สร้าง backend API, (ข) เรียก PostgREST และ RPC จากหน้าเว็บ |
